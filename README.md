# router-watchdog

Watchdog для Mihomo на Entware: проверяет текущую ноду, восстанавливает связь при её отказе и выбирает подходящую замену по свежему пингу и скорости. Замеры идут через отдельную скрытую группу и не переключают основную группу между кандидатами.

[Документация проекта](docs/README.md) · [Структура проекта](docs/project-map.md) · [Алгоритм](docs/failover-design.md) · [План и статус](docs/implementation-plan.md)

## Требования

- Entware, `/opt/bin/python3`, `python3-yaml`, `ca-bundle` и `wget-ssl` (зависимости устанавливаются через opkg).
- Mihomo с external controller API.
- Основная группа типа `select` с конкретными нодами из proxy-providers.
- Отдельная группа `BENCHMARK` с теми же нодами и HTTP listener для замеров.
- Работающий Entware `crond`, читающий `/opt/etc/crontab`.

Для чтения YAML Mihomo скрипт использует PyYAML (`python3-yaml`). Пакет имеет архитектуру `all`; Python и сертификаты устанавливаются из feed архитектуры роутера.

Установите зависимость для чтения YAML:

```sh
opkg install python3-yaml
```

## Установка и обновление

Скрипт установки публикуется начиная с версии 1.0.11; для прежних релизов используйте ручной способ ниже. Для установки через shell скачайте `install.sh` из последнего опубликованного релиза и запустите от пользователя с правами управления Entware:

```sh
curl -fL https://github.com/Arap919/router-watchdog/releases/latest/download/install.sh -o /tmp/router-watchdog-install.sh
sh /tmp/router-watchdog-install.sh
```

Если `curl` отсутствует, сначала установите его и сертификаты из штатного feed Entware. Скрипт проверяет opkg, обеспечивает HTTPS-загрузчик, идемпотентно добавляет feed и вызывает штатную установку/обновление пакета. Он не копирует payload вручную и не заменяет механизм сохранения пользовательского JSON. Альтернативная ручная установка:


Добавьте feed пакета:

```sh
FEED='src/gz router-watchdog https://arap919.github.io/router-watchdog/all'
grep -qF "$FEED" /opt/etc/opkg.conf || echo "$FEED" >> /opt/etc/opkg.conf
opkg update
opkg install router-watchdog
```

На Keenetic с MIPSel встроенный downloader иногда не поддерживает HTTPS и сообщает `wget: not an http or ftp url: https://...`. Сначала установите Entware `wget-ssl` из штатного feed:

```sh
opkg update
opkg install wget-ssl
opkg update
opkg install router-watchdog
```

Обновление установленного пакета:

```sh
opkg update
opkg upgrade router-watchdog
```

Если старый индекс содержит путь `/all/all/`, обновите индекс через `opkg update`: адрес пакета должен содержать только один компонент `/all/`.

Пакет поставляет шаблон `/opt/share/router-watchdog/defaults.json` и начальный JSON по пути `/opt/etc/router-watchdog.json` как обычный файл, без регистрации `conffile`. Сохранение пути в составе пакета предотвращает удаление JSON как устаревшего файла и последующую ошибку проверки хеша при переходе со старой регистрации `conffile`. Макрос `INSTALL_CONF` задаёт права файла `600`; регистрацию `conffile` он не включает. Окончательный основной JSON формирует механизм слияния из нового шаблона и сохранённых пользовательских настроек. При установке и обновлении пакет объединяет `/opt/etc/router-watchdog.json` с шаблоном новой версии `/opt/share/router-watchdog/defaults.json` перед синхронизацией cron. Заполненные пользовательские значения сохраняются только для ключей новой версии; остальные значения берутся из шаблона. `false` и `0` сохраняются, а `null`, пустая строка, список или объект считаются незаполненными. Вложенные объекты объединяются по полям, непустые списки переносятся целиком.

Перед распаковкой обновления исходный JSON временно сохраняется в `/opt/etc/router-watchdog.json-upgrade`, чтобы сохранить пользовательские данные до замены начальным JSON из пакета. После успешного слияния временная копия удаляется; при ошибке остаётся для повторной попытки и не перезаписывается следующим запуском установки. Исходный JSON сохраняется как `/opt/etc/router-watchdog.json-old` (копия предыдущего обновления заменяется), результат атомарно записывается в `/opt/etc/router-watchdog.json`. Оба файла создаются с правами `600`, поскольку могут содержать API secret. При ошибке чтения или записи слияние завершается с ошибкой, синхронизация cron не выполняется; исходные пользовательские данные остаются в копии `-upgrade`; основной JSON на этом этапе может содержать начальные значения пакета. Новые benchmark listener и другие настройки самого Mihomo по-прежнему нужно подготовить отдельно.

## Настройка Mihomo

Файл `myMihomoCongif.yml` — личный пример конфигурации, он не устанавливается пакетом. В нём `ПОДПИСКА PAPER` стоит первой в `proxy-groups` и в явном порядке встроенной `GLOBAL`. Имена существующих групп сохранены, чтобы правила продолжали ссылаться на них. Повторяющиеся списки нод оформлены YAML-якорем; состояния селекторов при этом независимы.

В исходном файле есть несоответствие `MATCH,Other` и имени группы `other`; правило оставлено без изменения. Нативная проверка Mihomo на этом компьютере недоступна, поэтому перед применением нужно отдельно устранить эту ссылку и проверить конфиг на роутере.

Добавьте фрагменты в соответствующие секции своего конфига:

```yaml
listeners:
  - name: benchmark-in
    type: http
    port: 17890
    listen: 127.0.0.1
    proxy: BENCHMARK
    users: []

proxy-groups:
  - name: BENCHMARK
    type: select
    use:
      - Paper
      - Paper-запасной-ключ
    hidden: true
```

Listener направляет запросы непосредственно в `BENCHMARK`. У этой группы должны быть доступны все ноды, которые watchdog может выбирать в основной группе. Основная и benchmark-группа должны различаться. Применение Mihomo-конфига на роутере выполняется отдельно.

## Конфигурация watchdog

Отредактируйте `/opt/etc/router-watchdog.json`:

```json
{
  "controller": "http://127.0.0.1:9090",
  "secret": "",
  "target_group": "ПОДПИСКА PAPER",
  "benchmark_group": "BENCHMARK",
  "benchmark_proxy": "http://127.0.0.1:17890",
  "top_n": 7,
  "healthcheck_parallelism": 6,
  "healthcheck_timeout_ms": 5000,
  "speed_connect_timeout_seconds": 5,
  "switch_wait_seconds": 0.7,
  "speed_test_url": "https://speed.cloudflare.com/__down?bytes={bytes}&cacheBust={cache_bust}",
  "download_bytes": 25000000,
  "parallel_streams": 4,
  "multi_rounds": 2,
  "log_cleanup_days": 3,
  "schedule": {
    "windows": [
      {"start": "07:00", "end": "01:00", "every_minutes": 1},
      {"start": "01:00", "end": "07:00", "every_minutes": 30}
    ]
  }
}
```

В пакетном JSON `target_group` намеренно пуст: укажите свою основную группу. API secret храните локально в конфигурации; watchdog отправляет его как Bearer token. Не добавляйте личные subscription URL или секреты в публичные материалы.

| Параметр | Значение и ограничения |
| --- | --- |
| `controller` | HTTP(S)-адрес API Mihomo; обязателен, без credentials в URL. |
| `secret` | Строка, по умолчанию пустая. |
| `target_group` | Имя основной группы `select`; обязательно. |
| `benchmark_group` | Отдельная группа `select`; по умолчанию `BENCHMARK`. |
| `benchmark_proxy` | HTTP(S)-адрес выделенного listener; по умолчанию `http://127.0.0.1:17890`. |
| `top_n` | Число кандидатов по последнему delay, `1..50`, по умолчанию `7`. Все ответившие кандидаты этого списка измеряются. |
| `healthcheck_parallelism` | Параллельные проверки кандидатов, `1..32`, по умолчанию `6`. Первичный поиск аварийной ноды последовательный, до первого успеха. |
| `healthcheck_timeout_ms` | Таймаут свежей проверки, `250..10000` мс, по умолчанию `5000`. |
| `speed_connect_timeout_seconds` | Таймаут соединения и ожидания данных потока, `1..30` секунд, по умолчанию `5`. |
| `switch_wait_seconds` | Пауза после выбора в `BENCHMARK`; конечное неотрицательное число, по умолчанию `0.7`. |
| `speed_test_url` | HTTP(S)-URL сервиса загрузки; поддерживает `{bytes}` (байт на поток) и `{cache_bust}` (метка времени). По умолчанию Cloudflare `__down`. Статическая ссылка тоже допустима. |
| `download_bytes` | Объём запроса каждого потока, `1000000..200000000` байт, по умолчанию `25000000`. |
| `parallel_streams` | Потоки в раунде, `1..8`, по умолчанию `4`. |
| `multi_rounds` | Раунды для каждой ноды, `1..4`, по умолчанию `2`; скорость — медиана раундов. |
| `log_cleanup_days` | Интервал очистки лога, `1..3650` дней, по умолчанию `3`. |
| `schedule.windows` | Суточные окна запуска в локальном времени роутера. |

Настройки замеров могут создавать существенный тестовый трафик: при базовых значениях успешный кандидат использует около `25 MB × 4 потока × 2 раунда = 200 MB`. Скачивание идёт через сервис из `speed_test_url`; по умолчанию Cloudflare Speed Test. Для статического файла выбирайте размер не меньше `download_bytes`: watchdog читает не больше этого объёма и отклоняет ответ короче 80% запроса. Старый JSON без нового поля продолжает использовать Cloudflare.

Прежние `fresh_top_n` и `close_result_percent` принимаются для совместимости старых JSON, но игнорируются с записью в лог. Больше нет дополнительного сокращения shortlist или выбора по проценту близости скоростей.

## Алгоритм

Провайдеры берутся из `proxy-groups[name=target_group].use` файла `/opt/etc/mihomo/config.yaml`. Каждое имя должно быть объявлено в `proxy-providers`. При отсутствии группы, непустого `use` или объявления провайдера запуск завершается с ошибкой. Остальные провайдеры и селекторы не опрашиваются и не обновляются. YAML читается с поддержкой якорей и ссылок; URL подписок не выводятся. При ручном обновлении скрипта установите зависимость: `opkg install python3-yaml`.

1. Проверить JSON и взять неблокирующую блокировку `/tmp/router_watchdog.lock`. При занятой блокировке записать пропуск и выйти.
2. Выполнить свежий healthcheck текущей ноды с настройками её провайдера. Если она доступна — завершить работу.
3. Получить конкретные provider-backed ноды из `target_group`, исключая названия с `Россия` или `Украина` без учёта регистра. Ноды того же провайдера вне группы не участвуют.
4. До замеров свежими проверками найти первую рабочую ноду и немедленно включить её в основной группе. Устаревший нулевой delay не запрещает аварийную проверку.
5. По последнему положительному историческому delay взять `top_n`, свежими проверками подтвердить доступность и измерить скорость всех ответивших через `BENCHMARK`.
6. Если нет истории, все shortlisted healthchecks или все speed tests неудачны либо аварийную ноду найти не удалось — один раз обновить только proxy-providers из `use` целевой группы, заново прочитать состав группы и свежими проверками проверить её допустимые ноды. Первую рабочую сразу включить в основной группе; затем взять `top_n` по свежей задержке и выполнить замеры.
7. Среди успешно измеренных нод найти минимальный свежий пинг. В диапазоне от него до `+50 мс` включительно выбрать максимальную скорость; при равной скорости — меньший пинг.
8. После всех замеров включить победителя в основной группе.

Если после восстановления подписок рабочих нод нет, watchdog завершится с ошибкой и записью в лог. Если рабочая аварийная нода есть, но все повторные замеры скорости провалились, она остаётся выбранной, а watchdog сообщает ошибку измерений. Частичный провал обновления провайдеров логируется; доступные ноды всё равно проверяются. При отказе API переключения нельзя считать связь восстановленной.

Healthcheck использует `/providers/proxies/{provider}/{node}/healthcheck`, провайдерские `testUrl` и `expectedStatus`. Старые `alive` и история не подтверждают доступность текущей ноды. У истории учитывается только последняя запись: `delay: 0` не заменяется более ранним успехом.

## Команды, лог и блокировка

```sh
/opt/bin/router-watchdog                 # обычная проверка
/opt/bin/router-watchdog --help
/opt/bin/router-watchdog --sync-cron
/opt/bin/router-watchdog --remove-cron
/opt/bin/router-watchdog --clear-log      # немедленная очистка
/opt/bin/router-watchdog --clear-log --if-due  # очистка по сроку

tail -f /opt/share/router-watchdog.log
```

Лог содержит время, этапы проверки, результаты healthcheck и раундов замера, обновления провайдеров, аварийный выбор и победителя. Сообщения также выводятся в stdout; cron не перенаправляет их повторно в тот же файл. Тела HTTP-ошибок контроллера не выводятся: они могут содержать приватные subscription URL.

Все действия, кроме справки, используют общую `fcntl.flock` блокировку. Файл блокировки не удаляется; дескриптор закрывается при завершении, в том числе при ошибке. Коды выхода: `0` — успех или пропуск занятого запуска; `1` — ошибка; `2` — отсутствующий обязательный конфиг.

Очистка проверяется cron ежедневно в 06:59. Срок хранится в `/opt/share/router-watchdog.log.cleanup`: при первой проверке начинается отсчёт без очистки существующего лога; после трёх прошедших суток следующая ежедневная проверка очищает лог. Ручная очистка сбрасывает срок. Неуспешная очистка не обновляет timestamp. Повреждённый timestamp вызывает ошибку, а не удаление лога. Пропущенный из-за блокировки ежедневный запуск повторится на следующий день.

## Cron и пути

`schedule.windows` задаёт `start`, `end` в формате `HH:MM` и целый `every_minutes` от `1` до `1440`. Начало включено, конец исключён; окна могут пересекать полночь. Совпадающие начало и конец означают сутки. Перекрывающиеся окна объединяются; пустой список отключает проверки нод, но сохраняет ежедневную задачу очистки.

```sh
vi /opt/etc/router-watchdog.json
/opt/bin/router-watchdog --sync-cron
```

Хук `/opt/etc/cron.1min/router-watchdog` синхронизирует настройки обычно в течение минуты. Предполагается, что Entware уже запускает `run-parts` для этого каталога. Синхронизация меняет только помеченные записи `/opt/etc/crontab` и перезапускает `/opt/etc/init.d/S10cron`, когда расписание изменилось. Записи содержат поле пользователя `root`.

Старые записи watchdog удаляются из `/opt/var/spool/cron/crontabs/root` и `/opt/etc/crontabs/root`, несвязанные задачи сохраняются. `crontab -l` показывает пользовательский spool, а не системный `/opt/etc/crontab`.

Пакет устанавливает:

```text
/opt/bin/router-watchdog
/opt/libexec/router-watchdog/router_watchdog.py
/opt/etc/router-watchdog.json
/opt/etc/cron.1min/router-watchdog
```

## Разработка и сборка

Локальные проверки из корня проекта:

```sh
python3 -m pip install PyYAML==6.0.3
python3 -m unittest discover -s tests -v
python3 -m py_compile net/router-watchdog/files/opt/libexec/router-watchdog/router_watchdog.py
sh -n net/router-watchdog/files/opt/bin/router-watchdog
sh -n net/router-watchdog/files/opt/etc/cron.1min/router-watchdog
git diff --check
```

Тесты подменяют сетевые операции; проверка роутера и сборка IPK выполняются отдельно. `net/router-watchdog/test.sh` предназначен для установленного пакета.

Определение пакета находится в `net/router-watchdog/Makefile`. GitHub Actions упаковывает этот скриптовый пакет напрямую средствами Python stdlib, без Docker, SDK, host tools и toolchain. Метаданные, пути, права и установочные hooks берутся из Makefile; поддерживается только текущий пакет `Architecture: all` с пустой стадией компиляции. Push в main и PR собирают IPK и feed как artifacts. Installer также сохраняется в том же artifact и публикуется рядом с IPK. Теги `v*.*.*` не пересобирают пакет: release-job находит успешную push-сборку main для точного SHA коммита тега, скачивает сохранённые IPK/feed и публикует release и GitHub Pages. Версия тега должна совпадать с `PKG_VERSION` и версией внутри IPK. Эти внешние действия выполняются только после отдельного решения о выпуске.

Для моделей ИИ точка входа — [AGENTS.md](AGENTS.md) и [проектный скилл](.agents/skills/router-watchdog-context/SKILL.md).

## MCP: замер скорости и подбор узла

Локальный MCP-сервер позволяет измерить выбранный узел и сравнить его с кандидатами через существующий `BENCHMARK`. Поиск по умолчанию возвращает результат без переключения. Установка, ограничения и подключение описаны в [инструкции MCP](tools/README.md).

## Выпуск из готовой сборки main

1. До merge задайте новую `PKG_VERSION` в `net/router-watchdog/Makefile`.
2. После merge дождитесь успешного `Build Entware package` для этого коммита main.
3. Поставьте тег `v<PKG_VERSION>` именно на этот коммит и отправьте тег.
4. Публикация загрузит `router-watchdog-ipk` и `router-watchdog-feed` из найденного run. Перед публикацией проверяются версия и архитектура IPK, совпадение пакета с feed, размер, SHA256 и сжатый индекс.

Сборки PR, другой ветки или другого SHA не подходят. Если main-сборка ещё идёт, завершилась неудачно либо артефакты отсутствуют/истекли, release завершается ошибкой: автоматической пересборки или выбора старого пакета нет. Повторно запустите исходную сборку main для того же коммита, дождитесь успеха и перезапустите workflow тега. Для ручной перепубликации уже выпущенного feed остаётся прежний `workflow_dispatch` с `release_tag`.

## Проверка и явная установка обновлений

```sh
router-watchdog --check-update
router-watchdog --install-update --expected-version 1.0.11-1
```

Команды возвращают JSON и работают без доступа к Mihomo и без заполненного `router-watchdog.json`. Проверка читает только опубликованный `update.json` feed и статус opkg. Доступная версия сравнивается численно с установленной; отсутствие управляемой установки возвращается как `installed_version: null`.

Установка выполняется только явно: запрошенная версия должна совпасть с текущим опубликованным релизом. Downgrade запрещён. Перед opkg проверяются фиксированный адрес пакета, размер, SHA256, имя, версия и архитектура из control metadata. После установки сверяется версия в opkg. При изменении доступного релиза нужно заново проверить обновления и подтвердить новую версию.

Обновления сериализуются отдельным lock `/tmp/router_watchdog_update.lock`: общий runtime-lock не удерживается через opkg, поскольку `postinst` вызывает `--sync-cron`. Не запускайте параллельно ручное редактирование JSON и установку пакета. Ошибка/отмена не означает rollback: opkg может уже применить часть изменений, поэтому перед повтором проверьте его состояние и сохранённые копии конфигурации.

Сам watchdog не рассылает уведомления и не ставит обновления автоматически. Периодическую проверку, уведомления и Web Push выполняет интеграция в Xkeen-UI PWA; она вызывает эти фиксированные команды. Значение `secret` контроллера ей для проверки обновлений не требуется. На старых версиях без этих CLI-флагов сначала нужно обновить пакет обычным способом.

Для локальной упаковки (каталог feed должен отсутствовать или быть пустым; для повторного запуска укажите новый `--feed-dir`):

```sh
python3 scripts/build_package.py --output-dir dist --feed-dir feed
```

Быстрая упаковка проверяется локальными тестами структуры, прав, hooks и manifest; это не заменяет проверку жизненного цикла opkg на реальном роутере.
