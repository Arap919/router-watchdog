# MCP для замеров Mihomo

Локальный сервер предоставляет пять инструментов через stdio. Они запускают фиксированные команды watchdog по SSH; секрет Mihomo и подписки остаются на роутере. MCP SDK нужен только на компьютере, дополнительные зависимости на роутере не появляются.

| Инструмент | Результат |
| --- | --- |
| `get_watchdog_config` | Чтение настроек и списка редактируемых полей; значение `secret` не возвращается. |
| `update_watchdog_config(changes)` | Частичное обновление только поддерживаемых настроек с проверкой до записи. |
| `measure_selected_node` | Активный замер загрузки выбранного узла: Мбит/с, свежая задержка, время UTC. |
| `find_faster_node()` | Такой же замер текущего узла и сравнение с кандидатами, без переключения рабочей группы. |
| `select_measured_node(node)` | Отдельный выбор любой успешно измеренной ноды после показа сравнения и явного выбора пользователя. |

Это пропускная способность тестовой загрузки, а не текущий пользовательский трафик и не гарантия скорости любого сайта. Оба MCP-инструмента замера используют быстрый профиль: **10 МБ на поток × 4 потока × 1 раунд = до 40 МБ на ноду**, до 320 МБ на текущую ноду и семь кандидатов. Профиль передаётся фиксированным CLI-флагом `--mcp-speed-profile` и применяется только к копии настроек текущего замера. JSON на роутере, обычный автоматический watchdog и прежние CLI-команды без этого флага сохраняют свои настройки.

Объём загрузки при прежних настройках 25 МБ × 4 × 2 уменьшается в пять раз. Фактическое время зависит от скорости нод, healthcheck и ошибок; ускорение времени в пять раз не гарантируется. Один короткий раунд чувствительнее к колебаниям: близкие значения скорости не означают устойчивого преимущества.

## Подготовка

1. На роутере должна быть установлена версия watchdog с CLI-флагами `--measure-selected`, `--find-faster`, `--get-config`, `--update-config` и `--select-node`, а также профилем `--mcp-speed-profile`. Сам MCP-сервер не устанавливает и не обновляет пакет. Старый watchdog с этими флагами не работает.
2. Настройте существующий `/opt/etc/router-watchdog.json`: рабочую группу, отдельную группу `BENCHMARK` и её proxy listener. Обе группы должны содержать конкретный выбранный узел из провайдеров `use` рабочей группы. Вложенные группы, DIRECT и исключённые имена стран для baseline не поддерживаются.
3. Настройте SSH-ключ и проверенную запись `known_hosts` обычным способом. Пароли и секреты не передаются через чат или аргументы инструментов. Сервер использует `BatchMode=yes` и `StrictHostKeyChecking=yes`.
4. На компьютере нужны Python 3.11+, OpenSSH и uv. Удобнее задать alias в `~/.ssh/config`:

```sshconfig
Host xkeen-router
    HostName 192.168.1.1
    User root
    Port 222
    IdentityFile ~/.ssh/id_ed25519_xkeen
    IdentitiesOnly yes
    AddKeysToAgent yes
    UseKeychain yes
```

Адрес и имя ключа замените своими. Приватный ключ не копируйте в репозиторий.

### SSH-ключ на Mac

MCP работает на компьютере и вызывает watchdog по SSH; отдельный MCP-процесс на роутере не нужен. На Mac создайте отдельный ключ (если его ещё нет):

```sh
ssh-keygen -t ed25519 -f ~/.ssh/id_ed25519_xkeen -C "xkeen-router"
ssh-add --apple-use-keychain ~/.ssh/id_ed25519_xkeen
```

Запрос `Enter passphrase` предлагает задать новую парольную фразу для защиты приватного ключа, а не ввести пароль роутера. Ввод не отображается. Рекомендуется задать фразу и добавить ключ в агент командой выше. Не перезаписывайте уже существующий ключ. Приватный файл остаётся на Mac; на роутер передаётся только файл `.pub`.

Установите публичный ключ, заменив адрес своим:

```sh
ssh-copy-id -i ~/.ssh/id_ed25519_xkeen.pub -p 222 root@192.168.1.1
```

Здесь запрашивается пароль root для SSH на роутере. `UseKeychain` и `--apple-use-keychain` относятся к macOS; на других ОС используйте обычный `ssh-add` и уберите `UseKeychain`.

### Особенность Entware Dropbear

В проверенной установке Entware Dropbear 2025.89 ключи root читаются из `/opt/etc/dropbear/authorized_keys`, а `ssh-copy-id` записал их в `/opt/root/.ssh/authorized_keys`. Поэтому успешное копирование ещё не гарантирует вход по ключу. Сначала проверьте установленный сервер и путь **на роутере**:

```sh
ps w | grep -E '[d]ropbear|[s]shd'
strings /opt/sbin/dropbear | grep -E '(/opt)?/etc/dropbear|authorized_keys'
ls -ld /opt/etc/dropbear
ls -l /opt/etc/dropbear/authorized_keys
```

Если бинарник показывает `/opt/etc/dropbear`, каталог существует, а файл ключей отсутствует, добавьте уже скопированные публичные ключи:

```sh
(
  umask 077
  cat /opt/root/.ssh/authorized_keys >> /opt/etc/dropbear/authorized_keys &&
  chmod 600 /opt/etc/dropbear/authorized_keys
)
```

Добавление сохраняет существующие записи; не заменяйте файл целиком, если там уже есть другие ключи. Дубликат корректного ключа не мешает входу. Перезапуск Dropbear не требуется. Это особенность сборки Entware, а не универсальный путь для всех SSH-серверов. См. [патч Entware](https://github.com/Entware/Entware/blob/master/package/network/services/dropbear/patches/100-pubkey_path.patch).

### Проверка перед подключением MCP

Сначала выполните обычный `ssh xkeen-router true`. При первом подключении проверьте отпечаток ключа хоста по доверенному источнику и подтвердите его, чтобы появилась запись `known_hosts`. Затем проверьте именно неинтерактивный режим:

```sh
ssh -o BatchMode=yes -o StrictHostKeyChecking=yes xkeen-router \
  /opt/bin/router-watchdog --get-config
```

Ожидается JSON настроек без запроса пароля. Только после этого подключайте MCP. Не отключайте проверку ключа хоста для обхода ошибки.

## Подключение

### Codex

Добавьте блок в `~/.codex/config.toml`. Пути замените на свои абсолютные: путь к uv можно узнать командой `command -v uv`.

```toml
[mcp_servers.xkeen-mihomo]
command = "/absolute/path/to/uv"
args = ["run", "--script", "/absolute/path/to/router-watchdog/tools/xkeen_mcp.py"]
startup_timeout_sec = 60
tool_timeout_sec = 1800

[mcp_servers.xkeen-mihomo.env]
XKEEN_SSH_HOST = "xkeen-router"
XKEEN_SSH_PORT = "222"
XKEEN_ALLOW_APPLY = "0"
```

Если блок сервера уже есть, измените его, не создавайте повторную TOML-таблицу. Сохраните файл и перезапустите подключение MCP в настройках клиента либо само приложение. Первый запуск uv может потребовать загрузки Python-зависимостей. Увеличенный тайм-аут инструмента нужен для сравнительных замеров.

Проверочный запрос: «Через xkeen-mihomo прочитай настройки watchdog». Он не запускает загрузку для замера скорости. Затем можно попросить измерить текущую ноду. Формат настройки описан в [официальной документации OpenAI](https://learn.chatgpt.com/docs/extend/mcp).

### Другие MCP-клиенты

Добавьте stdio-сервер в настройки вашего MCP-клиента, указав абсолютные пути к uv и скрипту:

```json
{
  "mcpServers": {
    "xkeen-mihomo": {
      "command": "/absolute/path/to/uv",
      "args": ["run", "--script", "/absolute/path/to/router-watchdog/tools/xkeen_mcp.py"],
      "env": {
        "XKEEN_SSH_HOST": "xkeen-router",
        "XKEEN_SSH_PORT": "222",
        "XKEEN_ALLOW_APPLY": "0"
      }
    }
  }
}
```

Это пример общей структуры MCP; конкретный формат настроек зависит от клиента. Зависимость `mcp>=1.20,<2` объявлена в самом скрипте и устанавливается uv отдельно от системного Python. Вариант без uv: установите эту зависимость в отдельное Python-окружение и запускайте скрипт его интерпретатором.

По умолчанию применение отключено. Для разрешения задайте `XKEEN_ALLOW_APPLY=1` локально и перезапустите MCP-сервер. Переключение выполняется только отдельным `select_measured_node(node)` после показа результатов и выбора конкретной ноды пользователем. У `find_faster_node()` больше нет параметра `apply`. Сам MCP не определяет, дал ли человек согласие: это обязанность клиента.

Примеры запросов: «Измерь скорость выбранного узла», «Подбери более быстрый, покажи сравнение». Даже на запрос «Подбери более быстрый и переключи» агент сначала показывает сравнение и ждёт выбора.

## Ошибки подключения и решения

### `Permission denied (publickey,password)`

`BatchMode=yes` запрещает запрос пароля. Ошибка означает, что вход по ключу не удался; ввод пароля от роутера в настройки MCP проблему не решает.

На Mac проверьте агент, фактическую SSH-конфигурацию и предлагаемый ключ:

```sh
ssh-add -l
ssh -G xkeen-router | awk '$1 ~ /^(hostname|user|port|identityfile|identitiesonly)$/'
ssh -vvv -o BatchMode=yes xkeen-router true 2>&1 | \
  grep -E 'Offering public key|Server accepts key|sign_and_send_pubkey|Authentications that can continue|Permission denied'
```

Если ключа нет в агенте, повторите `ssh-add --apple-use-keychain ~/.ssh/id_ed25519_xkeen`. Если предлагается правильный ключ, но нет `Server accepts key`, проверьте серверный путь из раздела Entware Dropbear, права и совпадение публичных ключей.

Войти на роутер по паролю для диагностики можно так:

```sh
ssh -p 222 -o PubkeyAuthentication=no root@192.168.1.1
```

На роутере проверьте домашний каталог и права:

```sh
awk -F: '$1=="root" {print FILENAME ": home=" $6 ", shell=" $7}' /etc/passwd /opt/etc/passwd
ls -ld /opt /opt/root /opt/root/.ssh
ls -l /opt/root/.ssh/authorized_keys
```

В проверенной установке владельцем был root, права каталогов `/opt` и `/opt/root` — `755`, `.ssh` — `700`, файла ключей — `600`. Правильные права в домашнем каталоге не помогают, если сервер читает другой файл.

Для сравнения ключей выполните на Mac `ssh-keygen -y -f ~/.ssh/id_ed25519_xkeen`, а на роутере — `awk '{print $1, $2}' /opt/root/.ssh/authorized_keys`. Тип и base64-часть должны совпасть; комментарий может отличаться. Приватный ключ и парольную фразу не публикуйте.

### Нет `logread` или журнал не объясняет отказ

На Keenetic команда `logread` может отсутствовать. Не перезапускайте основной SSH: в открытой сессии роутера временно запустите отдельный экземпляр на свободном порту локального адреса (замените адрес своим):

```sh
/opt/sbin/dropbear -F -E -p 192.168.1.1:223 -P /tmp/dropbear-debug.pid
```

В другом терминале Mac:

```sh
ssh -p 223 -i ~/.ssh/id_ed25519_xkeen -o IdentitiesOnly=yes root@192.168.1.1 true
```

Для нового порта может потребоваться отдельное подтверждение ключа хоста: проверьте отпечаток. Сообщение `Exit before auth` само по себе не означает отказ пользовательского ключа: клиент мог остановиться до аутентификации из-за неизвестного ключа хоста. `Password auth succeeded` подтверждает вход по паролю, а не исправность входа по ключу. После проверки остановите временный сервер через Ctrl+C; основной порт 222 продолжит работать. Не настраивайте внешний проброс диагностического порта.

### `Switching is disabled`

Локально установите `XKEEN_ALLOW_APPLY = "1"` в существующем блоке `[mcp_servers.xkeen-mihomo.env]`, сохранив SSH-параметры, и перезапустите MCP. Флаг разрешает отдельный выбор измеренной ноды; порядок «замер → таблица → выбор пользователя» сохраняется. Изменение файла без перезапуска не меняет окружение уже запущенного сервера.

### Сервер подключился, но инструментов нет или CLI не узнаёт флаг

Проверьте абсолютные пути к uv и `tools/xkeen_mcp.py`, перезапустите MCP для перечитывания схем инструментов. Обновление пакета на роутере не обновляет локальный скрипт на Mac и наоборот: обе стороны должны поддерживать описанный протокол. Ошибка `unrecognized arguments` от watchdog требует проверки версии установленного пакета (`opkg status router-watchdog`) и его обновления.

## Замер → сравнение → выбор

1. `find_faster_node()` измеряет текущую ноду и кандидатов без переключения рабочей группы.
2. Агент показывает таблицу всех успешных замеров: точное имя ноды, скорость Мбит/с, задержку, разницу с текущей; отмечает текущую ноду, сообщает время замера и неудачные замеры.
3. Пользователь выбирает ноду из таблицы либо оставляет текущую. Можно выбрать более медленную ноду, например ради задержки.
4. После выбора агент вызывает `select_measured_node(node)` с точным именем. Повторной загрузки нет: роутер проверяет принадлежность рабочей группе, свежую доступность и неизменность исходной выбранной ноды, переключает и проверяет результат. Выбор уже текущей ноды возвращает `applied=false`.

MCP хранит последний успешный сравнительный замер в памяти процесса. Узлы без успешного замера недоступны для выбора. Новый поиск сначала очищает прежние результаты, даже если закончится ошибкой. Успешный выбор (включая сохранение текущей ноды), изменение настроек через MCP или перезапуск сервера требуют нового сравнения. Между замером и выбором lock освобождён: cron продолжает работать; если текущий выбор изменился, требуется новое сравнение.

Описание инструментов задаёт этот порядок для агента. Сам MCP не рисует таблицу и не может проверить, видел ли её человек; показ и ожидание ответа обеспечивает MCP-клиент/агент. После обновления локального сервера перезапустите его, чтобы клиент перечитал схемы инструментов. На роутере нужна версия с новым `--select-node`; обновление пакета выполняется отдельно.

## Поведение

- Перед обеими операциями замера (CLI и MCP) `BENCHMARK` переключается на текущий узел `target_group`; результат проверяется до первого healthcheck. При ошибке синхронизации замеры не начинаются. Во время подбора `BENCHMARK` далее переключается между кандидатами.
- Весь тестовый трафик идёт с роутера через существующий `BENCHMARK`. Рабочая группа во время замеров сохраняется.
- Операции используют тот же `/tmp/router_watchdog.lock`, что и cron. При занятости возвращают `busy`; удалять lock-файл не нужно. Watchdog пропускает свои запуски, пока ручной тест держит блокировку.
- Для поиска свежие проверки выполняются для остальных допустимых членов рабочей группы, присутствующих в `BENCHMARK`. Из них до `top_n` с наименьшей свежей задержкой проходят замер скорости, дополнительно к baseline. Глобальный список провайдеров не запрашивается.
- Сравнение использует существующую `choose_winner`: максимум скорости среди результатов в окне минимальной задержки +50 мс. Победитель служит рекомендацией; отдельный выбор пользователя не ограничен этой рекомендацией. Победитель означает лучший измеренный результат в этом наборе, а не проверку всех узлов подписки.
- Ошибка baseline прекращает сравнение без переключения. Ошибка замера кандидата исключает его из результатов. Ручные операции не обновляют подписки и не запускают аварийный failover.
- Смена рабочей группы извне во время замеров прекращает операцию. Проверка и применение через API не атомарны: полностью исключить гонку с панелью невозможно. После применения выполняется проверка выбранного узла.
- Обычный cron продолжает работу после освобождения lock и позднее может изменить выбор при отказе узла.
- Каждый поток тестовой загрузки ограничен 60 секундами целиком, включая запуск процесса, соединение и чтение ответа. При превышении лимита процесс загрузки останавливается; сокетный тайм-аут остаётся дополнительным ограничением. Ошибка baseline прекращает поиск, ошибка кандидата исключает его из результатов.
- MCP сообщает фиксированные причины `download_timeout`, `download_http_error`, `download_network_error`, `download_incomplete` и `download_failed`. Сырые URL, токены, stderr и тексты исключений не передаются. Для остальных ошибок сохраняется общее сообщение; журнал содержит безопасный код отказа.
- SSH ожидает до 30 минут. При тайм-ауте или закрытии клиента операция на роутере может продолжиться; проверяйте состояние перед повторным запуском. Клиенту также нужен достаточный тайм-аут инструмента для длительных замеров.
- CLI возвращает JSON в stdout, журналы замеров идут в stderr и существующий файл. MCP не возвращает сырые SSH-ошибки и журналы модели; проверяйте их локально.

## Проверки без роутера

```sh
uv run --no-project --with PyYAML --with 'mcp>=1.20,<2' python -m unittest discover -s tests -v
```

Тест stdio запускает настоящий MCP-сервер и SDK-клиент с подставным SSH. Остальные тесты используют модель контроллера и моки загрузок. Они не подтверждают работу установленного пакета, реальную скорость или подключение к вашему роутеру.

## Сервис проверки скорости

Настройка `speed_test_url` в `/opt/etc/router-watchdog.json` используется и автоматическим watchdog, и MCP-замерами. По умолчанию:

```json
{"speed_test_url": "https://speed.cloudflare.com/__down?bytes={bytes}&cacheBust={cache_bust}"}
```

`{bytes}` заменяется на `download_bytes`, `{cache_bust}` — на текущее время в наносекундах. Допустимы только эти два шаблона, без форматирования, credentials и fragment. Можно указать HTTP(S)-ссылку на статический файл: он должен содержать не меньше запрашиваемого объёма. Загрузка ограничивается `download_bytes`; ответ короче 80% считается неудачным. Старые конфиги без поля используют прежний Cloudflare URL.

## Изменение конфигурации через MCP

Сначала вызовите `get_watchdog_config`: `config` содержит сохранённые поддерживаемые настройки без `secret`, `editable_fields` — разрешённые имена, `secret_configured` — признак наличия секрета. Legacy-поля, отсутствующие в пакетной схеме, не редактируются.

Пример аргументов `update_watchdog_config`:

```json
{
  "changes": {
    "speed_test_url": "https://example.com/large-test-file.bin",
    "top_n": 5
  }
}
```

Замените пример URL на свой доступный сервис. Сервер передаёт patch в stdin фиксированной SSH-команды, а не в shell-аргументы. Роутер проверяет имена, типы, диапазоны, URL и согласованность настроек, затем атомарно заменяет JSON с правами `0600` под общим lock. Неуказанные настройки и существующие legacy-поля сохраняются. Неизвестные поля и вложенные ключи отклоняются без записи. Ответ содержит только `updated_fields` и `cron_sync_required`, без значений настроек.

`schedule` передаётся целиком в виде `{"windows":[{"start":"07:00","end":"01:00","every_minutes":1}]}`. Поля окон строго ограничены `start`, `end`, `every_minutes`. Если расписание изменилось, `cron_sync_required=true`: JSON уже сохранён, но для применения расписания отдельно выполните штатный `router-watchdog --sync-cron` на роутере. MCP-обновление не меняет crontab и не перезапускает службы. Остальные настройки используются при следующем запуске операции.

`secret` принадлежит схеме и проходит проверку типа, но секреты следует изменять локально в конфигурации, не передавая через чат. Локальный флаг `XKEEN_ALLOW_APPLY` управляет только переключением узлов, а не редактированием JSON. Агент должен изменять настройки только по запросу пользователя.

Обычный автоматический watchdog и CLI `--find-faster --apply` сохраняют прежнее поведение. Новый CLI `--select-node` получает только `{ "node": "...", "expected_current": "..." }` через stdin; MCP не подставляет имена в SSH-команду.
